## 1. 里程碑与阶段对照

| 里程碑 | 包含阶段 | 验收标准(可执行) |
|---|---|---|
| **M0** 可行性闸门 | P0 | 见 `plan/overview.md` §8 的 17 项必做验证 |

## 3. 三条排期原则(冲突时按此裁决)

**① 先打通最窄的一条竖线,再横向铺开。**
不要"把 C ABI 写完整"再动 Lua 层。正确做法是:让 `add` 这**一个算子**从 `libpaddle`
一路贯通到 `x + y` 能在 Lua 里跑出正确结果,**再**去加第二个算子。
理由:竖线打通之前,任何一层的设计都是纸面推测;打通之后,剩下的是重复劳动。

**② 能交付的优先于完备的。**
P8(`jit::Layer` 推理)编号靠后,但排期应尽早 —— 它让"Python 训练 / Lua 推理"
在 P9 那 6 周还没开始之前就能交付。有真实用户比有完整 API 更能暴露设计错误。

**③ 测不了的往后放,但要写清楚"测不了"。**
P17 distributed 可以写,但验收标准里必须明写"当前环境无法验收"。
单卡下 `all_reduce` 是恒等映射,**永远看起来是对的** —— 这种代码不标注清楚就是负债。

## 4. 什么时候允许打乱顺序

| 情形 | 允许吗 | 说明 |
|---|---|---|
| P0 未通过就开始写 P1 | ❌ | 硬闸门。构建方案不定,C ABI 的形状就是猜的 |
| P3 只生成了 20 个算子就开始 P5 | ✅ | 符合原则 ①,鼓励 |
| P9 只写了 5 个层就开始 P10 | ✅ | Linear + ReLU 足够验证优化器 |
| 跳过 P6 直接做 P9 | ❌ | 没有 `backward()` 的 `nn.Layer` 无法验证 |
| 提前做 P18 | ❌ | 最难且收益最低,提前做必然返工 |
| P17 与 P12 换序 | ✅ | 无依赖关系,按人力方便安排 |

## 5. 每个阶段收工时必须做的三件事

1. 更新 `process/status.md`:阶段状态、变更日志、环境记录若有变化
2. 更新 `process/tasks.md`:勾掉完成项,把下一阶段拆成原子任务
3. 若过程中推翻了某个已定决策 -> 写进 `process/decisions.md` 的**翻案记录**,
   并同步 `CLAUDE.md` §2 决策台账

**三件事没做完,该阶段不算完工。**
