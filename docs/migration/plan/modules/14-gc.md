## 1. 做什么 / 不做什么

**做:** 让 Lua 的 GC 感知到 userdata 背后的巨量显存,并在压力下正确回收。

**不做:** 不改 Lua 的 GC 算法,不写自己的内存分配器。

**问题的本质:**

```
Lua 看到的           实际持有的
┌─────────┐         ┌────────────────────────┐
│ 64 字节  │ ──────► │  300 MB GPU 显存        │
│ userdata│         └────────────────────────┘
└─────────┘
```

Lua 的 mark-sweep 按**它自己分配的字节数**决定何时 GC。
64 字节的对象根本不足以触发 GC,于是显存先爆。

**这不是 bug,是所有"托管语言 + 非托管资源"组合的通病。**
Torch7 在 2011 年就遇到了并解决了 —— 我们抄它的答案。

## 3. 设计:九层,从便宜到昂贵

| 层 | 机制 | 触发时机 | 成本 |
|---|---|---|---|
| 1 | **堆追踪**:每次分配告诉 Lua "我用了 N 字节" | 每次张量分配 | 极低 |
| 2 | 批量上报(累积 1MB 才上报一次) | 同上 | 极低 |
| 3 | ×1.4 增长因子(避免频繁 GC) | 同上 | 极低 |
| 4 | `paddle.scope` 显式作用域 | 用户显式 | 零(用户承担) |
| 5 | `tensor:free()` 显式释放 | 用户显式 | 零 |
| 6 | **OOM 回调里 `lua_gc(LUA_GCCOLLECT)`** | 显存分配失败时 | 高,但只在濒死时 |
| 7 | 回调后重试分配 | 同上 | — |
| 8 | 仍失败 -> 抛可读的 OOM 错误(含显存统计) | 同上 | — |
| 9 | 5.4 的 `__close`(若可用)| 作用域退出 | 低 |

**前三层是 Torch7 的原方案,是主力。** 后面几层是我们加的保险。

### 3.1 堆追踪(第 1–3 层)

```c
/* 每次 pd_tensor 分配 */
static __thread int64_t pending = 0;
void pd_gc_account(int64_t bytes) {
  pending += bytes;
  if (llabs(pending) > 1024*1024) {           /* 第 2 层:1MB 批量 */
    lua_gc(L, LUA_GCSTEP, (int)(pending / 1024));
    pending = 0;
  }
}
```

**`__thread` 是必须的**(Torch7 也这么做)——
Lanes 下多个 lane 各有自己的 `lua_State`,共享一个计数器必然错乱。

> ⚠️ **实现回填(2026-10-29,T-M1-18 层1-3 实测)**:上面草图的
> `lua_gc(L, LUA_GCSTEP, ...)` **编不过 5.1/LuaJIT**——`LUA_GCSTEP`
> 是 5.2+ 引入的编译器常量(5.1 只有 `LUA_GCCOLLECT` 值=2)。落地 =
> `csrc/capi/gc.cc`(纯 C 计数,thread_local pending + 全局 atomic
> heapSize + thread_local softmax),handler 经 `pd_gc_set_handler`
> 注册、由 sol 层 `module.cc gc_softmax_bridge` 调
> `lua_gc(L, LUA_GCCOLLECT, 0)`(全版本存在,五版本约束 C5)。
> **finalizer 安全网**:`THGeneral.c:219` 的 `if (size > 0)` 被逐行
> 保留——**只有正分配触发 handler**,LuaTensor 析构(跑在 Lua GC
> finalizer 里)只合账不触发,绝无重入。被 @mikec 问到的
> ×1.4 增长:`gc.cc` 里 `after*10 > softmax*8`(整数化 0.8 阈值),
> 不是设计阶段的 `×8>×10` 直译。

### 3.2 OOM 回调(第 6–8 层)

```
显存分配失败
    │
    ├─► RegisterOOMCallback 触发
    │       │
    │       ├─ lua_gc(L, LUA_GCCOLLECT, 0)   全量回收
    │       └─ 返回"再试一次"
    │
    ├─► 重试分配
    │
    └─► 仍失败 -> 抛错,信息里带:
         已分配 X MB / 缓存 Y MB / 请求 Z MB / 建议:用 paddle.scope 或减小 batch
```

**最后那条建议很重要。** "CUDA out of memory" 这六个字对用户毫无帮助,
告诉他具体数字和下一步做什么才有价值。

**落地回填(2026-10-29,层6-8 已完成)**:C ABI Group 11 加 `pd_gc_register_oom` +
`pd_gc_fire_oom`(gc.cc)。注册时**强制 `FLAGS_offload_retry_times` > 0**(默认 -1,
`common/flags.cc:2363`;`retry_allocator.cc:67` 在 <=0 时整个跳过回调),然后
`RegisterOOMCallback(gc_oom_callback)`(公共 API,`retry_allocator.h:32`,
签名 `std::function<size_t(Place, size_t)>`)。回调体:**thread_local 重入守卫
`g_in_oom_callback`**(坑① 解)——已在回调内则返回 0(释放 0 字节 → 分配按原样失败),
否则跑**当前线程自己的 softmax bridge**(同一个 thread_local handler,module.cc 每
lane 在 luaopen 注册自己的 lua_State → `lua_gc(L, LUA_GCCOLLECT, 0)` 只动本线程的
state,坑② 的"lane 注册表 + 发信号"方案不需要——回调天然在失败线程上跑),然后返回
`tracked_bytes` 前后差值(freed>0 则 RetryAllocator 重试,`retry_allocator.cc:60-87`)。
**架构事实**:`RetryAllocator` 只包 GPU/XPU(`allocator_facade.cc:403/979/987/1408`),
CPU-only 构建的真实分配失败**不会**路由到回调 —— so 验收走 `pd_gc_fire_oom(fake_bytes)`
测试钩子(直接驱动已注册回调,同 `oom_smoke.cc` 已证的重试语义);GPU 真 OOM 路径留到
有卡环境(P7/P14 验收)再实证。sol 层:`core.gc_fire_oom` 绑定 + module.cc luaopen 尾部
调用 `pd_gc_register_oom()`(幂等;重载只是覆盖全局单例,回调体经 thread_local 找到
各自的 handler)。**GC_SMOKE 第 7 节 4 断言**:8MB 死壳 drop 后 `core.gc_fire_oom(0)`
返回 freed>0(回调的 lua_gc 回收了死 shell)、ledger 回落(不再持有死壳字节)、二次
触发返回 <1MB(无死壳可回收,且**不崩溃、不重入**)。

**落地回填(2026-10-29,层5 `t:free()` 已完成)**:LuaTensor 增 `free()` 方法
(sol_common.hpp)——置 `h=nullptr` + ledger **立即** `pd_gc_account(-tracked)` +
`pd_tensor_free(h)`。语义:**只删本 shell 的引用**(paddle::Tensor 里是 shared_ptr,
`pd_tensor_retain` 建的共享壳不受影响),幂等(二次 free 空操作)。dtor 改调 free()
——moved-from 壳(h==nullptr)与用户已 free 的壳在析构时天然 no-op
(`pd_tensor_free(NULL)` = delete nullptr, tensor.cc:229),**防 double-free**。
usertype 注册 `"free"`(tensor_binding.cc),Torch7 `tensor:free()` 镜像。**GC_SMOKE
第 8 节 3 断言**:1MB 张量 free() 后 ledger **立即**回落 base(不等 Lua GC 到达)、
二次 free 幂等不重复扣账、死壳 collect 后 dtor no-op 不双释放。**层9 `__close`**:
sol2 3.5 无 `meta_function::close`,`api/scope.md` §7 已标"不做也不阻塞"——九层里
1-3/4(scope 2.6 已交付)/5/6-8 全部落地,9 明确不做,3.3 机制层收口。

## 4. 已知的坑

**① `lua_gc` 在 OOM 回调里调用是危险的。** 回调可能在任意上下文触发,
包括 CUDA 驱动的内部路径。**必须验证它不会重入或死锁**(M0 第 7 项)。
如果不安全,第 6–8 层降级为"只报错不抢救"。
**✅ 已解(2026-10-29)**:回调体开头 `thread_local bool g_in_oom_callback`
守卫,已在回调内直接返回 0(释放 0 字节 → 分配按原样失败,不递归进
`lua_gc`);`oom_smoke.cc`(M0 第 7 项)已实测回调返回 0 时 RetryAllocator
只调一次就放弃的语义。另有一层天然保护:**回调只跑 `lua_gc(LUA_GCCOLLECT)`
在分配路径(正常 Lua 调用上下文),LuaTensor 析构(在 finalizer 里)只合账
不触发任何 handler**(`if(bytes>0)`,THGeneral.c:219)。

**② 多 lane 下 `lua_gc` 该调哪个 `lua_State`?** OOM 是全局的,
但 `lua_gc` 是针对单个 `lua_State` 的。
需要维护一个 lane 注册表,回调时对所有 lane 发信号 ——
**但不能跨线程直接调别人的 `lua_gc`**,那是数据竞争。
只能设标志位,让各 lane 自己在安全点回收。这是本阶段最难的一处。
**✅ 已解(2026-10-29)——不需要 lane 注册表**:RegisterOOMCallback 的
回调**天然跑在分配失败的那个线程上**,而 handler 是 `thread_local`
(gc.cc,每 lane 在 luaopen 注册自己的 lua_State)——回调直接调本线程
自己的 bridge → `lua_gc` 只动本线程的 state,天然满足"不跨线程调别人
的 lua_gc"。无 handler 的线程(非 Lua lane)返回 0,分配照常失败。
由"全局回调 + 线程局部 handler"组合替代"注册表 + 发信号"。

**③ LuaJIT 的 GC64。** 未开 GC64 的 LuaJIT 有 2GB 地址空间限制。
虽然张量数据在 GPU 上不占这 2GB,但**大量小 userdata 依然可能撞墙**。
M0 第 8 项验证构建是否开了 GC64,没开就在文档里警示。

**④ 堆追踪会让 GC 变频繁,可能拖慢训练。** 需要提供开关:
`paddle.set_heap_tracking(false)`。但**默认开启**(Torch7 先例,D-R3)。
