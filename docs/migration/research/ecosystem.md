## 1. 那句起点

> 「Torch7 把前端从 Lua 换成 Python,变成了 PyTorch;我又把 PaddlePaddle 的前端从 Python 搬回了 Lua。」

这句玩笑话底下有一个正确的技术事实,也正是整个项目可行的原因:
**PyTorch 早期的 `TH`/`THC` 就是 Torch7 的 C 核心原样搬过去的,换的只是前端。**
我们做的是同一件事的镜像 —— **Paddle 的 C++ 内核一行不动,只换前端**,
这也正是"零上游改动"那条红线的意义。

---

## 2. 核心判据:「语言无关」= C ABI + 一份内存描述协议

这一晚上最有用的一条,反复在三个不同话题上成立:

| 话题 | 表面问题 | 真实答案 |
|---|---|---|
| PIL 要不要迁到 Lua | 怎么翻译几万行 Python | **PIL 自己就不是 Python 写的**,重活在 libjpeg-turbo / zlib / FreeType。「迁移」= 给同一批 C 库写绑定 |
| numpy 怎么对齐 | 要实现多少函数 | numpy 的护城河**不是 API 是 buffer protocol / DLPack** —— 所有人都认那份"指针+shape+strides+dtype" |
| InsightPlot 怎么跨语言 | 要给几种语言写 API | 中间那层 **display list(场景描述)** 才是资产,前端可以有一百种,后端可以随便换 |

**推论:凡是"枚举具体类型/具体语言"的地方,基本都该换成"一份描述协议"。**
这与 `argrule` 里那条「容器是**协议**不是类名单」(R31)是同一条教训换了层皮 ——
我在 Lua 侧写成 `{"table","pl.List","insight.Array"}` 被推翻过一次,
在 C++ 侧对应的错误写法就是 `#ifdef` 逐个支持 `std::vector` / `std::array` / `void*`
(2^N 编译组合,测试面炸掉)。正确写法是一个最小输入结构 + 零成本适配器。

## 3. 索引惯例属于**绑定层**,不属于核心(→ R38)

Insight7 的既有架构已经把最难的决定做对了:

```
Insight7/
  src/  include/  backends/       <- C++ 核心,不属于任何一门语言
  bindings/
    python/   julia/   lua/       <- 三个绑定
```

于是"1-based 会不会赶跑 numpy 用户"这个矛盾自动消解 ——
**索引基准是绑定层的事**(R24 当初只说改 Lua 绑定,已经暗含了这条):

| 绑定 | 索引 | 内存序 | 理由 |
|---|---|---|---|
| Python | **0-based** | row-major | numpy 用户零重学 |
| Lua | **1-based** | row-major | Lua 母语惯例(D13 / R6 / R24) |
| Julia | **1-based** | **column-major** | Julia 本来就这样 |

**同一个核心,每种语言用它自己的惯例。**
Julia 那一列尤其说明问题:**连内存序都得在绑定层处理**,索引基准当然更是。

**对 paddle-lua 的意义:** 我们依赖的「Insight7 Lua 绑定是 1-based」不是一个临时补丁,
而是这条通则的一个实例 —— 它不会在 Insight7 加 Python/Julia 绑定时被回退。

## 4. 战略排序(讨论结论)

### 4.1 先做的是**协议**,不是**库**

| 事项 | 何时 | 理由 |
|---|---|---|
| Insight7 内存协议(DLPack 兼容?→ Q-22) | **最优先** | 真·关键路径:Tensor↔Array 零拷贝、DataLoader、Lanes 跨线程、将来 InsightPlot 全从它身上过。现在改最便宜,晚半年是三个仓库一起动 |
| display list 协议**写一页纸,不实现** | 顺手 | 它是内存协议的**第一个外部消费者** = 一次免费的压力测试。能干净引用 Insight Array 不拷贝不特判 = 协议定对了 |
| paddle-lua | 按 `WORKPLAN.md` 继续 | **不因等 Insight7 完整而停** |
| InsightPlot 实现 | 第一条真实 loss 曲线出现时 | 见 4.2 |

### 4.2 为什么 InsightPlot **不**先于 paddle-lua

1. **依赖方向是反的。** 绘图是训练**之后**的事,在依赖图上是**叶子**,不是上游。
   "感觉上底层"和"依赖图上游"是两回事。
2. **现在做一定做偏。** 没有真实需求约束,就只能照着 matplotlib 的功能表抄 ——
   而这正是 matplot++ 的病。等能训练了,头三张图是确定的
   (loss 曲线 / `imshow` 一批图 / 混淆矩阵),需求会直接告诉你协议该长什么样。
3. **生态不是靠库的数量,是靠一个跑通的故事。**
   反例就在眼前:**Torch7 自己的绘图库就是个 gnuplot 绑定**,烂得一塌糊涂,
   完全没耽误它成为生态 —— 因为它先把"读数据→训练→存模型→推理"跑通了。
   **"绘图必须先做好"这个前提,被 Torch7 自己证伪过一次。**

### 4.3 真要做时的技术路线(备忘,不是计划)

分层必须一开始就切对,否则会变成第二个 matplot++:

```
前端 API      pyplot 风格 / OO 风格 / Lua 表风格     <- 可以有一百种
─────────────────────────────────────────────
场景描述      display list:纯数据,可序列化         <- ★ 真正的资产
─────────────────────────────────────────────
渲染后端      SVG / PDF / 光栅(AGG) / GPU          <- 可以随便换
```

- **matplotlib 真正"语言相关"的只有三块**:pyplot 状态机 + Artist 树、布局引擎
  (tight/constrained layout)、mathtext(自带的 TeX 子集)。
  **画像素那层早就是 C++**(`_backend_agg.cpp` + Anti-Grain Geometry),字体是 FreeType。
  → 和 PIL 同一结论:难的是那层薄壳里的**设计决策**,不是像素。**[待核实]**
- **最大的坑是字体渲染**(FreeType + HarfBuzz + 中文 + 数学公式),能吞几个月。
  **SVG 后端可以完全绕过它** —— 输出是纯文本,字体交给显示端。
  所以顺序是:① display list 协议 ② SVG 后端 ③ 五个图元
  (`line/scatter/imshow/hist/bar` + 坐标轴 + 文本)④ 之后才是 PNG(那时才需要光栅化)。
  前三步是**一个周末**的量级,做完就能画训练曲线。
- matplot++ 用 gnuplot 的公道话:它白嫖了字体、坐标轴布局、十几种输出格式;
  代价是必须外挂进程、部署地狱、能力被 gnuplot 锁死。**[待核实:它现在是否仍是 gnuplot 后端]**

## 5. Insight7 对齐 numpy:判据与陷阱

### 5.1 「对齐 numpy」不能当作 paddle-lua 的前置条件

实测(2026-08-03,`python/paddle` 全部 `.py`,不含测试):

```
去重后用到的 np.* 符号:132 个        (numpy 公开 API 约 600)
出现次数前 34 名里,一半是 dtype 名与常量
真正的函数只有:array asarray copy zeros ones arange concatenate
                prod sum mean max abs round clip random.*
```

**一个完整的深度学习框架,它的整个 Python 前端靠十五个 numpy 函数活着。**

→ 第一步的完工判据不是"numpy 功能做完"(无底洞),
而是"**paddle-lua 用得到的那个子集做完**"(可量、可收口)。
→ 而且三步**不要串行**:先做那十几个 → 立刻跑通一次前向 → 回头补。
每一轮都有真实调用者拉着,做出来的东西不会歪。

### 5.2 但"慢慢对齐 numpy"这个长期目标本身是对的,且有独立的最短路径

> **「让 numpy 用户有更好的选择」的最短路径是 `bindings/python`,不是 Lua。**

因为 numpy 用户**就在 Python 里** —— 不需要等 Lua 生态,也不需要说服任何人换语言,
`pip install` 就能被评判。而 Lua 那条线的用户根本不是 numpy 用户,是 Lua 用户。
**两条独立的线,可以并行,互不阻塞。**

### 5.3 「没有 numpy 的包袱」要写成清单,否则会长回来

要扔的(讨论中列出的):`np.matrix`、**0-d array 与标量的混乱**、
value-based casting 那套 dtype 提升、`object` dtype、masked array(`np.ma`)、
C-order/F-order 双轨、**视图 vs 拷贝的不确定性**。
**要留的:广播规则** —— numpy 少有的设计得完全正确的东西。

⚠️ **扔掉包袱 ≠ 扔掉协议。** numpy 的价值 80% 在"所有人都认它那份内存描述"。
"没有包袱"若代价是"别人的数据进不来、我的数据出不去",那 API 再漂亮也是孤岛。

### 5.4 ★ 对齐名字容易,对齐语义要命

> 人的原话:「所以我觉得到时候我们要查阅一下 numpy 的代码,在开工的时候。」

同意,并且**该把 `CLAUDE.md` §4 的反幻觉范围从 Paddle 扩到任何外部 API**。
但读之前先排性价比 —— **numpy 的语义其实不在源码里**:

| 顺序 | 读什么 | 为什么 |
|---|---|---|
| ① | **Array API Standard**(`data-apis.org/array-api`)**[待核实 → Q-23]** | 据记忆,它正是"把 numpy 语义语言无关地标准化",且已剔掉 `np.matrix`/masked array、用严格类型提升取代 value-based casting,还带官方测试套件。若属实 = **一份现成的、包袱已剔的规格 + 别人吵完的设计决策 + 可直接跑的验收测试** |
| ② | `numpy/_core/tests/` | **测试才是可执行的语义规格。** 想知道"`reshape` 什么时候返回视图",读测试比读源码快十倍 |
| ③ | NEP(尤其 NEP 50) | 记的是**为什么**,以及**哪些是 numpy 自己承认的错误** —— 那些正是该扔的 |
| ④ | C 源码 `numpy/_core/src/multiarray/` | 极难读,且很多语义是"实现出来的"不是"设计出来的"。**只在前三份说不清时才读** |

**更省事的办法:别只靠读,用差分测试。**
目标既然是语义一致,判据就该是"同一批输入两边输出一致",而不是"我读懂了它的实现" ——
在 numpy 上跑几千 case dump golden,拿来对拍,**分歧会自己浮出来**。
这套设施 `plan/ci.md` §7 已经为 paddle-lua 设计好了,可直接复用。

⚠️ **但对拍有一个盲区,必须专门防**(已写进 `plan/ci.md` §7):
**视图 vs 拷贝对拍不出来** —— 两边输出的值完全一样,差别只在改了返回值之后原数组变没变。
这类**别名语义**必须专门设计测试:**动一下返回值,回头查原数组**。
它和 `requires_grad`/`stop_gradient` 是同一个性质:**不报错,只是结果错**。

## 6. 关于"没有 KPI 的压迫"

> 人:「毕竟我们没有 KPI 的压迫,其实可以慢慢对齐 numpy。」

同意,但这条红利的正确用法值得写下来:

> **没有 KPI 最大的红利不是"能做得更全",是"能推翻自己"。**

numpy 的包袱不是因为作者水平不够,是因为它**不能推翻自己** ——
value-based casting 大家都知道是错的,从提出到 NEP 50 落地花了十几年,
只因为它背着千万行存量代码。

而这一晚上,人推翻我四次、推翻自家协议一次,成本是零。
**这是这个项目唯一的结构性优势 —— 要花在"发现做错了就立刻改"上,不是花在"做得更全"上。**

⚠️ 同一枚硬币的反面(也记下来):**Agent 最擅长帮人做的事,恰恰是扩大范围。**
"顺便把 PIL 也迁了"这种念头,我一定会说"好的,这是设计文档",
然后就有两个都没做完的项目。**60% 的框架等于 0。**
